# Audit — 2026-07-30

Safety/security review focused on **data-loss risk**, plus an upstream check of Proton's
API and product direction. Conducted against `main` at v3.2.1, with the live daemon on
**Proton Bridge v3.25.0**.

Scope note: this pass deliberately prioritised paths where a bug destroys mail over paths
where a bug merely returns a wrong answer.

---

## 1. `remove_label` survival invariant — verified, and now test-covered

**Risk.** `remove_label` / `bulk_remove_label` are implemented as `\Deleted` + `EXPUNGE`
against the `Labels/<name>` mailbox (`SimpleIMAPService.deleteFromFolder` /
`bulkDeleteFromFolder`). That is non-destructive *only* because Bridge maps an expunge from
a label mailbox onto "remove this label" rather than "delete this message". The entire
safety of the operation rests on a Bridge-side mapping, not on anything mailpouch controls.

Bridge has been actively churning exactly that mapping:

| Change | Release | Effect |
|---|---|---|
| BRIDGE-485 | v3.24.0 | separated expunge-from-old-location from the unlabelling logic |
| BRIDGE-488 | v3.24.0 | reverted `RemoveFromMailbox` to pre-3.23.0 behaviour |
| BRIDGE-522 | v3.24.1 | restored the old unlabel endpoint behind a feature flag |

**Coverage gap found.** No test asserted the invariant. `bulk-audit.e2e.test.ts` seeds
messages *directly into the label folder* and then asserts only that they are gone from it —
an unlabel that permanently destroyed the message would pass identically. The Greenmail lane
cannot express this at all: there a `Labels/` mailbox is an ordinary folder, so a destructive
expunge is indistinguishable from a correct detach.

**Verified empirically (2026-07-30, Bridge v3.25.0).** Using a synthetic draft in a scratch
folder — no real mail involved — labelled it, unlabelled it, and confirmed it was removed
from `Labels/<name>` while surviving in its source folder. **The invariant holds today.**

**Closed by** a bridge-lane regression test in `test/e2e/scenarios/safe-bridge.e2e.test.ts`:
`remove_label detaches the label and leaves the message alive in its source folder`. It
asserts both halves — absent from the label *and still present in INBOX*. Bridge-only by
necessity.

**Action:** run the safe-bridge lane on every Bridge upgrade. This is the one invariant in
the codebase whose correctness is owned entirely by upstream.

## 2. Delete paths — sound

`deleteEmail` / `bulkDeleteEmails` move to Trash via the verified-landing `moveEmail` path;
they never expunge. A message already in Trash is a no-op success. Every `messageDelete`
(`\Deleted` + `EXPUNGE`) call site in `simple-imap-service.ts` is a sanctioned exception:

- `deleteFromFolder` / `bulkDeleteFromFolder` — label detach (see §1)
- `emptyTrash` — the single explicit permanent-delete tool: Trash-only, gated, `confirmed:true`

**Traversal check:** `deleteFromFolder` does *not* itself validate that its target is a
label mailbox, so its safety depends entirely on callers. Both callers (`remove_label`,
`bulk_remove_label`) hardcode the `Labels/` prefix and validate the leaf via
`validateLabelName` → `validateLeafName`, which rejects `/`, `..`, and control characters.
There is no agent-reachable way to aim that EXPUNGE at a normal mail folder.

## 3. Persistence and cache integrity — sound

- Atomic writes: `src/utils/atomic-json.ts` (tmp + `renameSync`) is used on the durable
  paths — config loader, escalation store, reminder service, scheduler. Remaining raw
  `writeFileSync` calls are legitimate: lock files (`flag: "wx"`), fd-scoped writes,
  `wx` backup files, and log truncation.
- UIDVALIDITY is tracked per folder (`uidValidityMap`); a change invalidates the email
  cache, and a *failed* check also clears it — failing safe in the exact case where a stale
  cache is most dangerous.

## 4. Session ownership (XPORT-016) — fixed and verified in production

Sessions were keyed by `Mcp-Session-Id` alone, letting any *other* authenticated agent
attach to a peer's session (`GET` → its SSE stream, `DELETE` → teardown). Fixed in #264 by
binding each session to the `client_id` that opened it. Verified against the live daemon:
a second agent presenting a peer's session id gets 400, the owner is unaffected, and the
rejection log records a 12-hex digest — the raw session id appears nowhere in the log.

## 5. Minor — error opacity

A Bridge-side `create_folder` rejection (e.g. attempting a top-level mailbox, which Proton
disallows) surfaces to the agent as `Error: An internal error occurred. See server logs for
details.` The underlying `Command failed` is only in the daemon log. Agents cannot
self-correct from that. Worth mapping common Bridge command failures onto actionable text —
here, "folders must be created under `Folders/` or `Labels/`".

## Upstream: Proton API and product direction (checked 2026-07-30)

**Still no public Proton Mail API.** Confirmed against the Spring/Summer 2026 roadmap —
there is no announced public/developer API for Proton Mail. The Go client
(`ProtonMail/go-proton-api`) remains an internal library for Proton's own clients; the
community "Proton API" documentation is explicitly unofficial and unsupported.
**Bridge IMAP/SMTP remains the only supported integration path, so mailpouch's architecture
is still the correct one.**

**Lumo API — new, and the first genuine third-party opening.** The Spring/Summer 2026
roadmap states Proton is "releasing a Lumo API that will let you add Lumo to your product or
software." No date given. This is the first Proton developer API aimed at third parties and
is worth tracking.

**Proton Drive SDK — still not third-party usable.** Per Proton's own January 2026 SDK
post: "Authentication and other Proton-specific modules required for standalone third-party
integrations are not yet supported." Basic file ops exist; sharing, photos, device
management and revisions do not. Official third-party support is tied to a cryptographic
model migration targeted **late 2026 / early 2027**. *This supersedes any plan to build on
the Drive SDK in the near term.*

**Proton Drive CLI — the viable near-term path.** A Drive CLI for Windows/macOS/Linux
covers upload/download, folder management, sharing and invitations, and is scriptable. For
mailpouch this is a far better integration target than the SDK, and mirrors the approach
already used for Proton Pass (`pass-cli`). *Corroborated across Proton's roadmap and SDK
posts; not yet installed or exercised locally.*

**Proton Mail roadmap item worth watching — Category view.** Automatic inbox categorisation
(Primary, Social, Promotions, Newsletters, Transactions, Updates). If these surface over
IMAP as new system folders or labels, they will appear in `get_folders` / `list_labels` and
change what agents see. Worth re-checking folder enumeration when it ships.

Other roadmap items (Calendar rewrite, VPN WireGuard client, Pass SSH agent, Drive Sheets /
Linux app) have no mailpouch surface. No Bridge/IMAP/SMTP changes and no SimpleLogin
updates appear in the roadmap.
